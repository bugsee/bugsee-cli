# `npm/` — the `@bugsee/cli` package family

Sources for the **six** npm packages published by
`.github/workflows/npm-publish.yml` (job `publish-optional-deps`):

```
@bugsee/cli                 front package: launcher + postinstall fallback, no binary
 ├─ @bugsee/cli-darwin-arm64    aarch64-apple-darwin
 ├─ @bugsee/cli-darwin-x64      x86_64-apple-darwin
 ├─ @bugsee/cli-linux-arm64     aarch64-unknown-linux-gnu
 ├─ @bugsee/cli-linux-x64       x86_64-unknown-linux-gnu
 └─ @bugsee/cli-win32-x64       x86_64-pc-windows-msvc

There is no Windows arm64 package — see bugsee/bugsee-cli#20 and the note in
`cli/lib/platforms.js`.
```

All six are published at the crate version, and the front package pins its
five `optionalDependencies` to that exact version — never a range. npm resolves
one of them by the `os`/`cpu` fields, so a consumer downloads one binary, not
five, and nothing has to run at install time. That is the difference from
`@bugsee/bugsee-cli` (generated by cargo-dist, one package whose `postinstall`
downloads the binary), which still publishes unchanged as an alias.

## Layout

| Path                         | What                                                                                                                                        |
| ---------------------------- | ------------------------------------------------------------------------------------------------------------------------------------------- |
| `cli/`                       | The front package, verbatim (its `package.json` is a template — `version` and the `optionalDependencies` values are stamped at build time). |
| `cli/lib/platforms.js`       | **The platform table.** The join key with `Cargo.toml`'s `[workspace.metadata.dist].targets` and cargo-dist's asset names.                  |
| `cli/lib/index.js`           | Runtime resolution + the programmatic `binaryPath()` export.                                                                                |
| `cli/bin/bugsee-cli.js`      | The `bin` launcher. Forwards argv/stdio/exit code.                                                                                          |
| `cli/scripts/postinstall.js` | The download fallback. Must never fail an install.                                                                                          |
| `build.mjs`                  | Assembles all six packages from a directory of release assets.                                                                              |

The five platform packages have no sources here: `build.mjs` mints each
`package.json` and `README.md` from the platform table, so adding a platform is
one row in `cli/lib/platforms.js` plus a triple in `[workspace.metadata.dist]`'s
`targets` in `Cargo.toml`. Do **not** run `dist generate` after that: the repo
sets `allow-dirty = ["ci"]`, which disables dist's WRITER as well as its check,
so `dist generate` is a silent no-op for `release.yml` — and clearing the flag
to force it would revert the hand-added `retention-days: 1` lines and the
dependabot-maintained `actions/checkout` pin. Verify with `dist plan
--output-format=json` instead; the build matrix is computed there at run time,
so a new triple needs no workflow edit. See the comment on `allow-dirty` in
`Cargo.toml`.

## Build locally

```sh
# 1. Fetch the release assets for a version (archives + .sha256 sidecars).
gh release download v0.7.5 --repo bugsee/bugsee-cli --dir /tmp/assets \
  --pattern 'bugsee-cli-*-*.tar.xz*' --pattern 'bugsee-cli-*-*.zip*'

# 2. Assemble. Every archive is SHA-256 verified against its sidecar.
node npm/build.mjs --artifacts-dir /tmp/assets --out npm/dist

# 3. Inspect.
( cd npm/dist/bugsee-cli-darwin-arm64 && npm pack --dry-run )
```

`--version X.Y.Z` asserts the assembled version matches `Cargo.toml` (CI passes
the release tag, so a workflow that checked out the wrong ref fails loudly
instead of publishing a mislabelled package). `--allow-missing` skips platforms
whose asset is absent — for local experiments only; CI must never use it.

## First-publish bootstrap

**Read this before the first release that includes these packages. The
automated publish CANNOT work until it is done, and the failure it produces
does not look like a configuration problem.**

npm's Trusted Publishing is configured on a **package's** settings page
(`npmjs.com/package/<name>/access`). That page only exists for a package that
has already been published — there is nowhere to pre-register a name. All six
names 404 on the registry today:

```sh
for n in @bugsee/cli @bugsee/cli-darwin-arm64 @bugsee/cli-darwin-x64 \
         @bugsee/cli-linux-arm64 @bugsee/cli-linux-x64 \
         @bugsee/cli-win32-x64; do
  printf '%-28s ' "$n"
  npm view "$n" version 2>/dev/null || echo "(not published)"
done
```

So the order is: **create the name, then add the trusted publisher, then let CI
take over.** Per name, once, by a human with publish rights on the `@bugsee`
scope:

1. **Publish a `0.0.0` placeholder with token auth**, from a scratch directory —
   not from `npm/dist`, which carries real content.

   ```sh
   npm login                      # or a granular publish token in ~/.npmrc
   tmp="$(mktemp -d)"
   for n in cli cli-darwin-arm64 cli-darwin-x64 cli-linux-arm64 \
            cli-linux-x64 cli-win32-x64; do
     mkdir -p "$tmp/$n"
     cat > "$tmp/$n/package.json" <<JSON
   { "name": "@bugsee/$n", "version": "0.0.0",
     "description": "Placeholder — see https://github.com/bugsee/bugsee-cli",
     "repository": "https://github.com/bugsee/bugsee-cli", "private": false }
   JSON
     npm publish "$tmp/$n" --access public
   done
   ```

   `--access public` is required: a scoped package defaults to restricted, and a
   restricted package is not installable. Do **not** pass `--provenance` here —
   it needs CI OIDC and will fail locally.

2. **Add the Trusted Publisher** on each package's settings page:
   `npmjs.com/package/@bugsee/<name>/access` → Trusted Publisher → GitHub
   Actions, with

   | Field               | Value                               |
   | ------------------- | ----------------------------------- |
   | Organization / user | `bugsee`                            |
   | Repository          | `bugsee-cli`                        |
   | Workflow filename   | `npm-publish.yml`                   |
   | Environment         | _(leave empty — the job uses none)_ |

   There is no API for this; it is a web-UI step, six times.

3. **Release normally.** `npm-publish.yml` publishes the real versions over the
   placeholders.

4. **Optional cleanup**, only _after_ step 3 has succeeded: `npm unpublish
@bugsee/<name>@0.0.0`. npm allows unpublishing a version within 72 hours.
   Never unpublish the _last_ remaining version — that deletes the package and
   with it the trusted-publisher configuration you just added, putting you back
   at step 1.

`@bugsee/bugsee-cli` already exists and already has its trusted publisher, so it
needs none of this.

### What it looks like if you skip it

`npm publish` fails with a **404 on the `PUT`**, which reads as though the
package does not exist rather than as a missing trust configuration. That is
also why the publish loop in `npm-publish.yml` is written to be resumable: a
half-bootstrapped first run fails partway through, and npm versions are
immutable, so without that the version would be permanently unfinishable. Fix
the missing entries, re-run the workflow, and it continues from where it
stopped.

## Publishing order matters

Platform packages first, front package last. Publishing the front package
first leaves a window in which `npm install @bugsee/cli` resolves optional
dependencies that do not exist yet — npm skips missing optional deps
_silently_, so the install succeeds with no binary and the failure only shows
up when someone runs the CLI. `npm-publish.yml` enforces the order inside one
job.
